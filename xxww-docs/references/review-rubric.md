# 文档审查量表

## 目录

1. 阻断级问题
2. 结构质量
3. 内容真实性
4. 可执行性
5. 可持续性
6. 审查输出

## 1. 阻断级问题

发现以下问题时先修复：

- 文档指示会破坏数据、泄漏密钥、绕过权限或执行错误生产操作。
- active 文档中的命令、端口、目录、接口或事实源与当前代码直接矛盾。
- 计划或 demo 被写成生产完成态。
- 已删除路径仍被当作唯一入口。
- 同一强约束在两处互相冲突且没有优先级说明。
- 根级 `CLAUDE.md` 或 `AGENTS.md` 缺失，或 `CLAUDE.md` 包含 `@AGENTS.md` 之外的内容。

## 2. 结构质量

- `AGENTS.md` 是否能在短时间内给出定位、红线、验证和索引？
- 完整项目树是否只在一个权威位置维护？
- 每篇文档是否有单一问题域，标题是否能表明用途？
- 功能文档是否与功能代码按相同节奏变化？
- 局部 README 是否保持短小并指向系统级规则？
- 历史稿是否与 active 文档物理或状态隔离？
- `docs/` 根是否只含宪章 + `features/` + `others/`？根级平铺的非宪章文档按结构发现处理，即使它有入链。
- `docs/others/` 是否有 README 决策表，且每篇有去留建议？
- 文档是否从稳定索引可达？

## 3. 内容真实性

逐项用代码验证：

- workspace 数量、包名、公开导出和依赖方向；
- 应用组合根、路由、注册表与真实 adapter；
- 数据库、schema、migration 和数据所有权；
- IPC/API/CLI 接口与认证边界；
- feature flag、fallback、兼容债和删除条件；
- 版本、端口、环境变量和部署拓扑；
- 测试命令、CI job 和发布路径。

对数字、枚举和“唯一”“全部”“永不”等绝对词做额外核验。它们最容易随代码漂移。

## 4. 可执行性

- 命令是否可从声明的目录运行？
- 前置依赖、危险副作用和环境要求是否清楚？
- 失败时是否有诊断入口、回滚或停止条件？
- 新文件放哪是否能通过一组互斥问题判断？
- 质量门槛是否连接到真实测试，而不是口号？

## 5. 可持续性

- 每条重要事实是否有明确变化触发器？
- 可从源码生成的内容是否避免手抄？
- 是否存在重复清单、重复命令或重复架构图？
- 文档改动是否和代码改动处于同一变更序列？
- 错误记录是否提炼预防信号，而不是只描述结果？
- 决策记录是否包含背景、选择、后果和替代方案？
- `AGENTS.md` 是否声明单个代码文件行数上限（默认 ≤1000 行），且无超限源码文件（`docs_audit.py` 的 `code-file-too-long`；生成物、vendored、快照除外）？

## 6. 审查输出

按严重度输出发现：

- `P0`：会导致安全、数据或生产事故。
- `P1`：当前事实错误，会显著误导实现或运维。
- `P2`：结构重复、索引断裂、状态不清，会加速漂移。
- `P3`：措辞、格式或低风险可读性问题。

每条发现包含：文档位置、代码证据、影响、最小修复。先呈现发现，再概括整体质量；没有证据时不下结论。
